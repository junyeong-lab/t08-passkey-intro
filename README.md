## 1. 무엇으로 붙였나 — 구현 방식

WebAuthn 표준을 사용하며 인증 검증은 Supabase Edge Function(Deno)에서 **`@simplewebauthn/server@14.0.3` 라이브러리**로 구현했습니다. 데이터 보관은 Supabase PostgreSQL을 이용합니다. 인증 서비스에 로그인 절차 전체를 맡긴 방식이 아닌, 라이브러리를 활용한 서버 측 직접 구현입니다.

### 무엇을 만들었는가

기존 T01의 Home·About 공개 자기소개는 유지하고, 그 아래에 **패스키 인증 후에만 비공개 자료를 내려받는 공간**을 구현했습니다. WebAuthn 패스키의 등록·로그인·추가·목록·삭제를 지원하며, 비밀번호를 입력받지 않습니다. `demo-a`와 `demo-b`라는 독립 테스트 계정에 각각 가상 프로젝트 메모·가상 지원 목록·가상 회고 3건이 있습니다. 2026-10-16 DB 조회 기준 계정마다 패스키 1개, 비공개 자료 3건이 남아 있습니다.

## 2. 왜 이런 방식을 선택했는가

브라우저의 HTML에 비공개 내용을 미리 넣은 뒤 CSS로만 가리는 방식이라면 '소스 보기'와 비로그인 직접 요청으로 내용이 드러날 수 있습니다. 따라서 공개 화면에는 설명만 넣고, **비공개 본문은 인증된 요청이 있을 때만 서버가 반환**하도록 설계했습니다.

패스키는 서버에 비밀번호나 개인키를 보관하지 않고, 사용자의 인증 기기가 만든 서명을 서버의 등록 **공개키**로 검사할 수 있습니다. 서버는 로그인한 계정의 자료만 조회해 URL에서 계정 ID를 바꿔도 다른 계정 자료가 섞이지 않도록 했습니다.

## 3. 어디를 어떻게 고쳤나 — 인증 흐름과 코드 위치

| 위치 | 구현 내용 |
| --- | --- |
| `index.html` | **공개 UI는 한 HTML 파일**에 유지. T01 공개 소개·패스키 등록/로그인 화면·인증 후 비공개 카드·테스트 검증 도구 |
| `supabase/functions/t08-passkey/index.ts` | WebAuthn 등록/인증 옵션 및 검증, 1회 질문, 토큰 발급·폐기, 계정별 비공개 읽기, 패스키 삭제 |
| `t08_accounts` | 테스트 계정 별칭과 ID |
| `t08_passkeys` | Credential ID, **공개키**, 검증 카운터, 패스키 이름 및 등록 메타데이터 |
| `t08_challenges` | 등록/로그인 질문, 용도, 계정, 만료·사용 상태 |
| `t08_sessions` | 무작위 세션 토큰의 **SHA-256 해시**, 계정·패스키 연결, 만료·폐기 상태 |

**네 가지 요청의 소스 위치:** 등록은 `index.html`의 `t08-register` 및 추가 패스키 등록 화면 → Edge Function `register-options`/`register-verify`; 로그인은 `t08-login` → `login-options`/`login-verify`; 로그아웃은 UI 로그아웃 버튼 → Edge Function `logout`; 비공개 조회는 인증 뒤 UI 메모 조회 → Edge Function `GET ?op=private`(타 계정 검사 `GET ?op=private-for`). 인증 구현 위치는 `supabase/functions/t08-passkey/index.ts`의 `handle` 함수입니다.

이들 5개 DB 테이블은 **RLS 활성화 상태**를 실제 Supabase 쿼리로 확인했습니다. 비공개 내용은 HTML 소스에서 직접 출력하지 않고 API 조회 성공 이후 DOM `textContent`로 넣습니다.

## 4. 어떻게 인증하고 시험했는가

**등록** — 브라우저가 `register-options`를 요청하면 서버가 고유 질문을 생성·저장합니다(5분 유효). 인증 기기는 개인키를 자체 보관하면서 WebAuthn 등록 응답을 만듭니다. 브라우저가 `register-verify`에 `flowId`와 `response`를 제출하면 서버가 origin, RP ID, 사용자 확인, 등록 응답을 검증하고 **공개키만** DB에 저장합니다. 정상 응답은 HTTP 201입니다. **2026-10-16 신규 검증 계정 `demo-c23`의 실제 Chrome Network에서 `register-verify` HTTP 201과 요청 Payload 필드 `flowId`, `response`를 확인했습니다.** 내부 WebAuthn 응답에서 `attestationObject`, `authenticatorData`, `clientDataJSON`, `publicKey`, `publicKeyAlgorithm`, `transports`, `type`을 확인했고, 개인키 전송용 필드는 확인되지 않았습니다. 이는 개인키가 인증기 내부에 보관되는 WebAuthn 구조 및 서버 공개키 저장 코드와 부합합니다. **원시 바이너리 내용 전체를 독립적으로 해독·감사한 것은 아니며 제출용 이미지의 Credential ID 등 마스킹은 별도 진행해야 합니다.**

### 등록 질문·공개키·로그인 질문의 실제 서버 기록 (C20·C22·C28)

2026-10-16 Supabase에서 기존 기록을 **조회만** 했으며 키와 질문을 새로 생성하거나 삭제하지 않았습니다. 질문 지문은 저장된 challenge 문자열에 `md5()`를 적용해 앞 12자만 표기한 **비교용 식별 지문**입니다. 인증용 해시가 아니며, 지문이 다르면 원본 질문 값도 다릅니다.

| 조건 | 계정·용도 | 서버 저장 질문의 비교용 지문 1 | 비교용 지문 2 | 판단 |
| --- | --- | --- | --- | --- |
| C20 | `demo-c23` 등록 질문 | `9fdda62c84f1` | `a1eaa5fd8256` | 서로 다름 |
| C28 | `demo-a` 로그인 질문 | `931b4e9d3dca` | `81e24bf8ac5b` | 서로 다름 |

**C22 서버 저장 공개키의 실제 값:** `t08_passkeys.public_key_b64url`에서 검증용 가상 계정 `demo-c23`의 `c23 검증키`를 읽어 확인했습니다. 아래 103문자는 **COSE 공개키를 Base64URL로 인코딩한 값**이며 개인키·비밀번호·세션 토큰이 아닙니다. Credential ID, 계정 UUID 및 세션 토큰은 기재하지 않았습니다.

```text
pQECAyYgASFYIEKOmU22FkVlchdD4zJJsUHWAxfR5qnqFCXhnftvZUYPIlggnF0ztmCWk0F8JzVupUQeFNceNFfYY1YWmJAQV89i0d4
```

**로그인** — 서버가 로그인 질문을 발급하고 기기가 서명합니다. 서버는 `verifyAuthenticationResponse`로 저장된 공개키·서명·질문·origin·RP ID를 검증합니다. 성공해야만 32바이트 난수 토큰을 발급하며, 토큰은 현재 브라우저 탭의 `sessionStorage`에, 해시는 DB에 저장하고 유효기간은 30분으로 설정했습니다. `logout`은 서버의 세션을 폐기합니다.

**계정 경계** — 인증이 없으면 `GET /private`은 HTTP 401을 반환합니다. 인증이 있어도 `private-for?account_id=상대계정`은 HTTP 403으로 거절합니다. `private?account_id=상대계정`으로 값을 바꿔도 서버가 세션의 소유 계정만 조회합니다. 이 구조는 실제 **양방향**(`demo-b → demo-a`, `demo-a → demo-b`)에서 상대 계정 직접 접근 HTTP 403, URL에 상대 계정 UUID를 위조해도 반환된 자료는 본인 소유, 요청 전후 본인 자료 수 3→3건으로 확인했습니다(2026-10-16).

### 필수 네 가지 검사 — 통과 요청과 거절 요청 비교 (C50)

| 확인 대상 | 정상 통과 요청·응답 | 차단할 요청·응답 | 확인 근거 |
| --- | --- | --- | --- |
| 로그인 없이 비공개 자리 열기 | 패스키 정상 로그인 후 `GET ?op=private` → **200**, 본인 가상 자료 3건 | 로그인 토큰 없이 `GET ?op=private` → **401**, 비공개 본문 미반환 | 이전 브라우저 요청·응답 |
| 남의 패스키로 다른 계정 자료 읽기 | 본인 세션으로 `GET ?op=private-for&account_id=본인` → **200**, 본인 자료 | `demo-a ↔ demo-b` 각각 상대 `account_id` 직접 요청 → **403**; URL만 상대 ID로 위조한 `GET ?op=private` → **200**이나 본인 자료만 반환 | 사용자 확인 양방향 요청 및 전후 자료 3→3 |
| 이미 사용한 로그인 질문 재사용 | 정상 `POST ?op=login-verify` → **200** | 동일 `flowId`·서명 재전송 → **409** | 브라우저 재사용 검증 기록 |
| 패스키 하나 삭제 뒤 로그인 | `demo-a` 첫 키 삭제 → **200**, 남은 두 번째 키로 로그인·자료 조회 성공(**200**) | 삭제한 첫 번째 Credential ID를 지정해 `POST ?op=login-options` → **403** | 사용자 인증·삭제 기록 및 DB |

C50의 마지막 403은 **삭제한 Credential ID에 대한 새 로그인 질문 발급 거절**을 관찰한 값입니다. 실제 삭제된 개인키로 서명을 생성해 검증 요청을 보낸 시험이었다고 주장하지 않습니다. 이 비교 표는 기존 수행된 검사를 정리한 것이며 추가 시험을 수행했다는 뜻은 아닙니다.

**2026-10-16 양방향 검증 재확인:** `demo-a`를 기존 기기의 두 번째 패스키로 인증한 후 `demo-b` 비공개 자료를 직접 요구했을 때 HTTP 403이 반환되었습니다. 상대 UUID를 본인 조회 URL에 입력한 요청도 서버가 본인 `demo-a` 자료만 반환했고, 전후 자료는 3→3건으로 유지됐습니다. 검증 후 Supabase 조회에서 두 계정 모두 패스키 1개, 메모 3건이 남아 있음을 확인했습니다. **계정 UUID와 개인 식별 정보는 최종 증빙에서 가립니다.**

패스키 보관 장소 선택 UI의 `device`는 **사용자가 선택한 기록값**이며 실제 저장 관리자와 구분합니다. **2026-10-16 사용자 화면에서 Chrome의 Google 비밀번호 관리자 패스키 목록에 `t08-passkey-intro.vercel.app`의 `demo-b` 항목이 저장되어 있음을 직접 확인**했고, 앞서 `demo-b`의 Google 계정 기반 PIN 인증 및 로그인 성공도 확인했습니다. 그러므로 `demo-b`의 현재 저장 관리자는 **Google 비밀번호 관리자**로 기록합니다. 같은 화면에 `demo-a` 항목도 표시되지만, 이전에 서버에서 삭제한 Credential ID의 잔존 항목인지 서버에서 아직 허용되는 패스키인지 일치 여부가 확인되지 않았습니다. **목록에 보인다는 사실만으로 현재 유효한 `demo-a` 패스키라고 판정하지 않습니다.** 두 항목을 삭제하거나 수정하지 않습니다. **사용자 확인에 따르면 `demo-a`는 기존 PC 화면의 QR 코드를 휴대전화 카메라로 스캔해 인증한 교차 기기 패스키(WebAuthn cross-device authentication) 방식**이었습니다. 지문·얼굴 인식 또는 Windows Hello를 사용했다고 단정한 이전 설명은 잘못된 것이므로 정정합니다. 추가로 사용자가 **갤럭시에서 확인한 Google 비밀번호 관리자 화면**에서 사이트 `t08-passkey-intro.vercel.app`의 `demo-a`(생성일 2026-10-15), `demo-b`(2026-10-16) 두 항목이 표시된 것을 확인했습니다. 따라서 **갤럭시의 Google 비밀번호 관리자에 해당 사이트 패스키 항목이 존재**한다는 근거는 확보했습니다. 다만 `demo-a`로 QR 교차 기기 인증 시 실제로 사용한 서버 등록 Credential ID와 관리자에 보이는 항목의 Credential ID를 직접 대조하지 못했으므로 **남은 두 번째 패스키의 저장 위치까지 확정하지는 않았습니다.**

## 5. AI가 도운 일과 내가 직접 확인한 판단

- AI는 공개 T01 화면을 유지한 `index.html`/Supabase WebAuthn 인증 코드 작성과 오류 검토, 검증 항목 정리 및 SQL 조회를 지원했습니다.
- 사용자는 서로 다른 기기에서 패스키 등록·로그인·삭제를 실제로 실행하고, 요청 성공/거절 화면과 자료 유지 여부를 직접 확인했습니다. 특히 '통과 조건 검증'과 '남길 것 증빙'을 구분해 **과제에서 요구하지 않은 추가 캡처는 제출하지 않기로 결정**했습니다.
- 다른 PC에서 `demo-a` 인증이 실패했을 때 기기의 기존 패스키를 강제로 삭제·재등록하지 않고, **기존 PC에서 확인할 때까지 해당 시험을 보류**했습니다. 사용자가 최종 문구를 확인하기 전까지 이 항목은 제출용 개인 소감으로 확정하지 않습니다.

## 6. 차단하지 못한 경우·제약과 후속 보완

**C43·C46 확인:** 패스키 목록 UI는 등록된 각 키의 **이름과 등록 날짜**를 표시합니다. `demo-a`가 두 개를 등록했던 시점의 목록 확인 기록이 있고 첫 번째 삭제 후 남은 두 번째 키로 재로그인했습니다. 화면에는 **모든 패스키를 잃으면 복구할 수 없으므로 마지막 한 개의 서버 삭제를 거절한다**는 안내가 있으며, 사용자가 실제로 마지막 한 개 삭제를 요청한 경우 **HTTP 409**를 확인했습니다. 만약 기기 분실 등으로 사용 가능한 키가 **0개**가 되면 로그인할 수 없고 서비스 자체 계정 복구 수단도 없습니다. 이는 마지막 한 개 삭제를 막는 기능과 다른 한계입니다.


서버는 마지막 패스키 **삭제 요청**을 HTTP 409로 거절하도록 구현했습니다. 그러나 **등록된 패스키를 사용할 수 있는 모든 기기와 동기화된 저장소를 잃어버렸을 때 계정을 복구하는 별도 수단은 구현하지 않았습니다.** 이는 실제로 기능이 없는 제약이며, 기기 분실을 재현해 악용/실패 여부를 실증한 것은 아닙니다.

또한 다른 기기에서 사용할 수 없는 패스키는 브라우저에서 `NotAllowedError`가 날 수 있습니다. 현재 사례에서는 실제 저장 관리자·기기 동기화 상태를 확인하지 못해 오류 원인을 단정하지 않습니다. 검증 후 후속 보완할 항목은 **기기/관리자별 등록 안내와 별도 복구 절차**입니다.

## '남길 것' / '제출할 것' 분리

**남길 것(원문 대조 완료):** 카드 1 공개·비공개 경계 화면/비로그인 응답 본문; 카드 2 등록 요청·응답 기록/실제 서버 저장 공개키/패스키 목록; 카드 3 성공 로그인 요청·실패 요청/이미 쓴 질문 재사용 요청·거절 응답; 카드 4 두 개 패스키 목록/하나 삭제 뒤 로그인 성공·실패 기록; 카드 5 네 가지 확인의 요청·응답/인증 구현 설명서 6개 항목. 그 외 시험용 화면은 과제 요구 증빙이라고 주장하지 않습니다.

**제출할 것:** 배포 URL, GitHub 소스(최종 소스 커밋·전체 구현을 확인할 수 있는 링크), 이 설명서의 정확한 요구 항목, 확인 4줄, AI와 내 판단 3줄, 원문 '남길 것'에서 요구한 필수 증빙. 이 설명서나 체크리스트 자체를 '실제 테스트 결과'의 대체 증빙으로 사용하지 않습니다.

**보안 점검:** 저장소의 공개 파일에는 실제 로그인 세션 토큰·PIN·개인키 문자열이 없음을 별도 코드 검사로 확인했습니다. **사용자가 촬영한 Windows 보안 인증 창에는 실제 이메일이 표시됐으므로, 그 이미지를 제출할 경우 이메일을 마스킹해야 합니다.** 계정 UUID/전체 Credential ID/세션 토큰은 제출용 사진에서 노출하지 않습니다.
