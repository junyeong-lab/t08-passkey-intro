> 2026-10-16 확인 기준. 이 문서의 `확인`은 실제 화면 응답·Supabase 조회·저장소 소스 점검으로 확인한 내용만 뜻합니다. **최종 제출 확정본이 아닙니다.**

## 1. 무엇을 구현했는가

기존 공개 자기소개를 수정 없이 볼 수 있도록 유지하면서, 비공개 공간의 가상 프로젝트 메모·지원 계획·회고는 패스키 인증 뒤에만 서버에서 가져오도록 했습니다. 테스트 별칭 `demo-a`, `demo-b`로 각각 패스키를 등록하고 계정별로 가상의 자료 3건씩 보관합니다. 비밀번호 없이 WebAuthn 패스키 등록·로그인, 질문 재사용 거절, 등록 패스키 확인·삭제, 계정별 자료 격리를 구현했습니다.

## 2. 왜 이렇게 설계했는가

브라우저 HTML에 비공개 문장을 미리 넣고 화면에서 가리는 방식으로는 소스 보기나 직접 요청으로 내용이 노출될 수 있습니다. 비공개 원문은 Supabase DB에 두고, Edge Function이 **패스키 인증 뒤 발급한 유효 세션**을 검증한 후에만 계정 소유 자료를 반환합니다.

WebAuthn은 기기가 개인키로 서명하고 서버가 등록 공개키로 서명을 검증합니다. 서버 코드에는 개인키 저장 필드가 없으며 DB의 패스키 레코드는 공개키·Credential ID·카운터 등을 저장합니다. `register-verify`의 브라우저 요청은 WebAuthn 등록 응답(증명 데이터)을 전송하도록 구현되어 있습니다. 다만 **실제 Network 등록 요청 본문 캡처는 아직 미확보**이므로 C23을 통신 증빙까지 통과했다고 표기하지 않습니다.

## 3. 어느 파일과 서버를 수정했는가

| 위치 | 역할 |
| --- | --- |
| `index.html` | 공개 Home/About, 패스키 등록·로그인 버튼, 비공개 카드 렌더링, 검증 도구 |
| `supabase/functions/t08-passkey/index.ts` | 등록·로그인 WebAuthn 검증, 질문·세션, 자료 조회, 패스키 삭제 API |
| Supabase `t08_*` 테이블·RPC | 계정·공개키·1회 질문·세션 해시·가상 자료 및 원자적 질문 소비/삭제 |
| Supabase RLS | 위의 5개 테이블 모두 RLS 활성화 상태를 DB 조회로 확인 |

등록 시 서버는 `generateRegistrationOptions`로 질문을 만들고 유효기간 5분인 레코드로 저장합니다. `verifyRegistrationResponse`에서 origin/RP ID/사용자 확인을 검사한 후 공개키를 저장합니다. 로그인 시 `verifyAuthenticationResponse`로 서버의 저장 공개키·질문·origin/RP ID를 검증합니다. 32바이트 난수 세션 토큰은 브라우저 탭의 `sessionStorage`에 보관하고 서버에는 SHA-256 해시와 30분 만료 시간을 저장합니다.

자료 API는 인증된 세션의 계정 ID로만 조회합니다. `private-for`의 상대 계정 UUID 요청은 HTTP 403으로 거절하며, `private`에 상대 `account_id`를 URL로 전달하더라도 세션 소유 계정 자료만 조회합니다. 마지막 패스키 삭제는 HTTP 409로 거절하도록 구현했습니다.

## 4. 어떻게 확인했는가 — 실제 확인 기록

1. **공개/비공개 경계:** 비로그인 상태 `GET /private` → HTTP 401; 비공개 본문을 전송하지 않는 화면·응답 확인.
2. **등록·로그인:** 실제 패스키 등록 및 공개키 저장 확인. 로그인 질문 10개 모두 서로 다른 값임을 DB에서 확인. 실제 패스키 인증 후 가상 메모 3건 조회 성공.
3. **인증 우회 거절:** 이미 사용된 질문·서명 재전송 HTTP 409, 실제 서명 한 글자 변조 HTTP 403. 정상 서명 로그인과 실패 요청 모두 화면으로 확인.
4. **복수 패스키·계정 분리:** `demo-a`에서 두 패스키 등록 후 첫 키 삭제 HTTP 200, 삭제 ID 로그인 질문 HTTP 403, 남은 두 번째 키로 재로그인 성공. `demo-b` → `demo-a` 상대 자료 직접 요청 HTTP 403, URL 값 위조 조회 시 `demo-b` 자료 3건만 반환, 거절 전후 3→3건 유지. 두 계정 각각 패스키 1개와 가상 자료 3건을 DB 조회로 확인.

**아직 확인하지 않은 것:** `demo-a` → `demo-b` 반대 방향 검증. 현재 `demo-a`의 패스키가 등록된 기존 PC를 사용할 수 없어 보류했습니다. 타 PC의 `NotAllowedError`는 미동기화·취소·사용자 확인 실패 등의 가능성을 포함하며, 정확한 원인은 확인되지 않았습니다.

## 5. AI가 도운 일과 직접 확인할 판단

- **AI 활용:** 기존 T01 공개 화면을 보존하면서 T08 UI 및 서버 인증 흐름의 구현·소스 점검을 지원했습니다.
- **AI 활용:** 정상/거절 응답을 항목별로 나누고, DB 저장 건수 및 보안 경계를 재점검했습니다.
- **직접 확인할 판단(미확정):** 패스키 보관 위치는 UI 선택값과 실제 브라우저/인증 관리자 저장 위치가 다를 수 있으므로 사용자가 확인해야 합니다. 또한 최종 제출 문구가 실제 사용자 판단을 정확히 반영하는지 확인이 필요합니다.
