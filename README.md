## 1. 무엇을 만들었는가

기존 T01의 Home·About 공개 자기소개는 유지하고, 그 아래에 **패스키 인증 후에만 비공개 자료를 내려받는 공간**을 구현했습니다. WebAuthn 패스키의 등록·로그인·추가·목록·삭제를 지원하며, 비밀번호를 입력받지 않습니다. `demo-a`와 `demo-b`라는 독립 테스트 계정에 각각 가상 프로젝트 메모·가상 지원 목록·가상 회고 3건이 있습니다. 2026-10-16 DB 조회 기준 계정마다 패스키 1개, 비공개 자료 3건이 남아 있습니다.

## 2. 왜 이런 방식을 선택했는가

브라우저의 HTML에 비공개 내용을 미리 넣은 뒤 CSS로만 가리는 방식이라면 '소스 보기'와 비로그인 직접 요청으로 내용이 드러날 수 있습니다. 따라서 공개 화면에는 설명만 넣고, **비공개 본문은 인증된 요청이 있을 때만 서버가 반환**하도록 설계했습니다.

패스키는 서버에 비밀번호나 개인키를 보관하지 않고, 사용자의 인증 기기가 만든 서명을 서버의 등록 **공개키**로 검사할 수 있습니다. 서버는 로그인한 계정의 자료만 조회해 URL에서 계정 ID를 바꿔도 다른 계정 자료가 섞이지 않도록 했습니다.

## 4. 어떻게 인증하고 시험했는가

**등록** — 브라우저가 `register-options`를 요청하면 서버가 고유 질문을 생성·저장합니다(5분 유효). 인증 기기는 개인키를 자체 보관하면서 WebAuthn 등록 응답을 만듭니다. 브라우저가 `register-verify`에 `flowId`와 `response`를 제출하면 서버가 origin, RP ID, 사용자 확인, 등록 응답을 검증하고 **공개키만** DB에 저장합니다. 정상 응답은 HTTP 201입니다. **브라우저 Network에서 실제 `register-verify` 요청·응답을 캡처한 증빙(C23)은 아직 확보하지 않았습니다.** 따라서 실제 패킷 본문 검사 완료로 표시하지 않습니다.

**로그인** — 서버가 로그인 질문을 발급하고 기기가 서명합니다. 서버는 `verifyAuthenticationResponse`로 저장된 공개키·서명·질문·origin·RP ID를 검증합니다. 성공해야만 32바이트 난수 토큰을 발급하며, 토큰은 현재 브라우저 탭의 `sessionStorage`에, 해시는 DB에 저장하고 유효기간은 30분으로 설정했습니다. `logout`은 서버의 세션을 폐기합니다.

**계정 경계** — 인증이 없으면 `GET /private`은 HTTP 401을 반환합니다. 인증이 있어도 `private-for?account_id=상대계정`은 HTTP 403으로 거절합니다. `private?account_id=상대계정`으로 값을 바꿔도 서버가 세션의 소유 계정만 조회합니다. 이 구조는 실제 **양방향**(`demo-b → demo-a`, `demo-a → demo-b`)에서 상대 계정 직접 접근 HTTP 403, URL에 상대 계정 UUID를 위조해도 반환된 자료는 본인 소유, 요청 전후 본인 자료 수 3→3건으로 확인했습니다(2026-10-16).

**현재 확보된 정상·실패 사례**

| 요청/상황 | 확인된 결과 | 확인 방법 |
| --- | --- | --- |
| 비로그인 비공개 자료 직접 조회 | HTTP 401, 비공개 본문 없음 | 사용자 브라우저 시험 |

| 로그인 서명 한 글자 변조 | HTTP 403 거절 | 실제 브라우저 요청 |

| 등록 HTTP 요청·응답 원문 | **증빙 미확보** | 새 패스키 등록 가능한 기기 필요 |


**2026-10-16 양방향 검증 재확인:** `demo-a`를 기존 기기의 두 번째 패스키로 인증한 후 `demo-b` 비공개 자료를 직접 요구했을 때 HTTP 403이 반환되었습니다. 상대 UUID를 본인 조회 URL에 입력한 요청도 서버가 본인 `demo-a` 자료만 반환했고, 전후 자료는 3→3건으로 유지됐습니다. 검증 후 Supabase 조회에서 두 계정 모두 패스키 1개, 메모 3건이 남아 있음을 확인했습니다. **계정 UUID와 개인 식별 정보는 최종 증빙에서 가립니다.**

패스키 보관 장소 선택 UI의 `device`는 **사용자가 선택한 기록값**이며 실제 저장 관리자와 구분합니다. **2026-10-16 사용자 화면에서 Chrome의 Google 비밀번호 관리자 패스키 목록에 `t08-passkey-intro.vercel.app`의 `demo-b` 항목이 저장되어 있음을 직접 확인**했고, 앞서 `demo-b`의 Google 계정 기반 PIN 인증 및 로그인 성공도 확인했습니다. 그러므로 `demo-b`의 현재 저장 관리자는 **Google 비밀번호 관리자**로 기록합니다. 같은 화면에 `demo-a` 항목도 표시되지만, 이전에 서버에서 삭제한 Credential ID의 잔존 항목인지 서버에서 아직 허용되는 패스키인지 일치 여부가 확인되지 않았습니다. **목록에 보인다는 사실만으로 현재 유효한 `demo-a` 패스키라고 판정하지 않습니다.** 두 항목을 삭제하거나 수정하지 않습니다. **사용자 확인에 따르면 `demo-a`는 기존 PC 화면의 QR 코드를 휴대전화 카메라로 스캔해 인증한 교차 기기 패스키(WebAuthn cross-device authentication) 방식**이었습니다. 지문·얼굴 인식 또는 Windows Hello를 사용했다고 단정한 이전 설명은 잘못된 것이므로 정정합니다. 추가로 사용자가 **갤럭시에서 확인한 Google 비밀번호 관리자 화면**에서 사이트 `t08-passkey-intro.vercel.app`의 `demo-a`(생성일 2026-10-15), `demo-b`(2026-10-16) 두 항목이 표시된 것을 확인했습니다. 따라서 **갤럭시의 Google 비밀번호 관리자에 해당 사이트 패스키 항목이 존재**한다는 근거는 확보했습니다. 다만 `demo-a`로 QR 교차 기기 인증 시 실제로 사용한 서버 등록 Credential ID와 관리자에 보이는 항목의 Credential ID를 직접 대조하지 못했으므로 **남은 두 번째 패스키의 저장 위치까지 확정하지는 않았습니다.**

## 5. AI가 도운 일과 내가 직접 확인한 판단

- AI는 공개 T01 화면을 유지한 `index.html`/Supabase WebAuthn 인증 코드 작성과 오류 검토, 검증 항목 정리 및 SQL 조회를 지원했습니다.
- 사용자는 서로 다른 기기에서 패스키 등록·로그인·삭제를 실제로 실행하고, 요청 성공/거절 화면과 자료 유지 여부를 직접 확인했습니다. 특히 '통과 조건 검증'과 '남길 것 증빙'을 구분해 **과제에서 요구하지 않은 추가 캡처는 제출하지 않기로 결정**했습니다.
- 다른 PC에서 `demo-a` 인증이 실패했을 때 기기의 기존 패스키를 강제로 삭제·재등록하지 않고, **기존 PC에서 확인할 때까지 해당 시험을 보류**했습니다. 사용자가 최종 문구를 확인하기 전까지 이 항목은 제출용 개인 소감으로 확정하지 않습니다.

## 6. 차단하지 못한 경우·제약과 후속 보완

서버는 마지막 패스키 **삭제 요청**을 HTTP 409로 거절하도록 구현했습니다. 그러나 **등록된 패스키를 사용할 수 있는 모든 기기와 동기화된 저장소를 잃어버렸을 때 계정을 복구하는 별도 수단은 구현하지 않았습니다.** 이는 실제로 기능이 없는 제약이며, 기기 분실을 재현해 악용/실패 여부를 실증한 것은 아닙니다.

또한 다른 기기에서 사용할 수 없는 패스키는 브라우저에서 `NotAllowedError`가 날 수 있습니다. 현재 사례에서는 실제 저장 관리자·기기 동기화 상태를 확인하지 못해 오류 원인을 단정하지 않습니다. 검증 후 후속 보완할 항목은 **기기/관리자별 등록 안내와 별도 복구 절차**입니다.

## 재현·확인 방법 — 4줄 (현재 검증 상태에 맞춘 초안)

1. 공개 주소를 비로그인으로 열어 T01 소개가 보이고 비공개 본문이 HTML에 없으며 `GET /private`가 **HTTP 401**인지 확인했습니다.
2. `demo-a`와 `demo-b`에서 패스키로 로그인해 각각 가상 자료 3건을 조회했고, 서버에는 계정별 공개키가 등록되어 있음을 확인했습니다. 단 **C23의 Network 등록 본문 증빙은 미확보**입니다.
3. 로그인 서명 변조 **HTTP 403**, 일회용 질문·서명 재사용 **HTTP 409**, 로그아웃한 토큰의 자료 조회 **HTTP 401**을 확인했습니다.
4. **양방향** `demo-b → demo-a`, `demo-a → demo-b` 접근 시 각각 **HTTP 403** 거절과 상대 UUID 위조 시 **본인 자료만 반환**, 거절 전후 **3→3건 유지**를 확인했습니다.

## AI와 내 판단 — 3줄 (사용자 최종 승인 전 초안)

1. **AI에 맡긴 일:** 기존 자기소개를 유지하는 웹 UI와 WebAuthn 서버 인증 흐름의 코드 작성·점검, 통과 조건과 서버 기록의 비교를 맡겼습니다.
2. **내가 직접 판단한 일:** 실제 패스키 인증과 두 계정의 자료 분리 상태를 확인했으며, 증빙은 과제 원문의 '남길 것'에 적힌 것만 정리하도록 했습니다.
3. **AI 제안 중 채택하지 않은 일:** 통과와 무관한 추가 화면의 제출, 다른 PC에서 접근되지 않는 패스키를 강제로 다시 등록하거나 삭제하는 방식은 채택하지 않았습니다.

## '남길 것' / '제출할 것' 분리

**남길 것:** 과제에서 지정한 공개·비공개 경계 및 비로그인 응답, 등록 요청·응답과 저장 공개키/패스키 목록, 로그인 정상·실패·재사용 거절, 패스키 복수 등록/삭제 후 로그인 기록, **양방향** 계정 접근통제 요청·응답. 실제 과제 원문의 목록·형식과 최종 대조 후 **해당 항목만** 제출합니다.

**제출할 것:** 배포 URL, GitHub 소스(최종 소스 커밋·전체 구현을 확인할 수 있는 링크), 이 설명서의 정확한 요구 항목, 확인 4줄, AI와 내 판단 3줄, 원문 '남길 것'에서 요구한 필수 증빙. 이 설명서나 체크리스트 자체를 '실제 테스트 결과'의 대체 증빙으로 사용하지 않습니다.

**보안 점검:** 저장소의 공개 파일에는 실제 로그인 세션 토큰·PIN·개인키 문자열이 없음을 별도 코드 검사로 확인했습니다. **사용자가 촬영한 Windows 보안 인증 창에는 실제 이메일이 표시됐으므로, 그 이미지를 제출할 경우 이메일을 마스킹해야 합니다.** 계정 UUID/전체 Credential ID/세션 토큰은 제출용 사진에서 노출하지 않습니다.
